# GitHub CV 배포

`AGENTS.md`와 `doc/site-guide.md`를 먼저 읽는다. 배포 전 검사만 요청된 경우에는 파일을 수정하거나 커밋·push하지 않는다. 커밋·push는 사용자가 명시적으로 요청한 경우에만 수행한다.

## 배포 전 점검

1. `git status --short`, 현재 브랜치, 원격 저장소, upstream을 확인한다. 사용자가 만든 변경과 현재 작업의 변경을 구분하고, 범위를 확정할 수 없으면 커밋 대상 파일을 사용자에게 확인한다.
2. `$verify-cv-site-content`를 사용해 공개 페이지의 섹션·표시 순서·특허·논문 노출·링크·자산·테마·반응형을 점검한다. 공개 가능한 경력, 학력, 프로젝트, 연락처만 포함하는지 확인한다.
3. 커밋 대상의 텍스트 파일을 검사한다. 토큰, API 키, 비밀번호, 개인 키, `.env` 값, 개인 전화번호, 비공개 문서 URL, 미공개 특허의 초록·문서 URL이 있으면 배포를 중단한다. 비밀값 자체는 출력·기록하지 않고 파일과 항목 종류만 보고한다.
4. `_site/`, `.jekyll-cache/`, `vendor/`, 임시 파일, 운영체제 메타데이터 등 생성물·불필요 파일이 커밋 대상에 없는지 확인한다. 필요한 로고·이미지는 `assets/images/`의 로컬 공개 자산인지 확인한다.
5. `git diff --check`를 실행한다. `$build-jekyll-cv` 절차에 따라 의존성을 확인하고 `bundle exec jekyll build`를 실행한다. Liquid 오류, 누락 자산, 실패한 빌드가 있으면 배포를 중단한다.
6. `_config.yml`의 `url`, `baseurl`, GitHub Pages 대상 브랜치·경로가 사용자 사이트 또는 프로젝트 사이트 형태와 일치하는지 확인한다. 실제 Pages 상태를 확인할 권한이나 도구가 없으면 검증 불가로 보고하고 배포 성공을 주장하지 않는다.

## 커밋과 push

1. 모든 사전 점검이 통과하고 사용자가 push를 명시적으로 요청한 경우에만 진행한다.
2. 검토한 파일만 명시적으로 stage하고, `git diff --cached`로 커밋 내용을 다시 확인한다. `git add -A`와 무차별 stage는 사용하지 않는다.
3. 짧은 명령형 커밋 메시지를 사용한다. 기존의 관련 없는 변경은 커밋에 포함하지 않는다.
4. 확인한 원격 저장소와 현재 브랜치의 upstream으로 일반 `git push`를 실행한다. `--force`, `--force-with-lease`, 원격 브랜치 삭제는 사용하지 않는다.
5. 원격 저장소 또는 upstream이 없거나 대상 브랜치가 불분명하면 push하지 않고 사용자에게 대상 정보를 요청한다.

## 배포 후 확인과 보고

1. push한 커밋 해시와 원격·브랜치를 확인한다.
2. GitHub CLI 또는 GitHub Pages의 관찰 가능한 배포 결과가 있으면 최신 배포 상태와 URL을 확인한다. 관찰 결과가 없으면 push 완료와 배포 확인 불가를 구분해 보고한다.
3. 결과에는 점검 통과 항목, 민감 정보 검사 결과, 빌드 결과, 커밋·push 여부, 배포 상태 또는 차단 사유를 간결히 기록한다.
